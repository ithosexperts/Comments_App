# Task Activity Feed — Python / FastAPI

A Python migration of the original Apps Script task-comments/activity feed. The app supports Message, Ask, Reply, attachments, active-employee @mentions, the User tab, task-specific comments, and a vertical layout with task details at the top and activity history below.

**Data access:** SQL Server is accessed only through the existing PHP CRUD APIs. The Python app does not open direct SQL Server/ODBC connections. Use `apiv2.php` for Test and `apiv3.php` for Production.

**Authentication:** In production, the sender identity comes from the authenticated One Portal session through a short-lived signed launch ticket. The browser may not choose the sender email. The One Portal integration files are in `one_portal_integration/` because the existing One Portal backend is a separate application and needs the router added to its current code.

## Run locally on Windows

From the repository root (the folder containing `run_local.py` and `app/`):

```powershell
py -3 -m venv .venv
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
Copy-Item .env.example .env
notepad .env
python run_local.py
```

Then open `http://127.0.0.1:8000/`.

`run_local.py` loads `.env` before selecting defaults. The example config targets **Test** (`SQL_API_MODE=test`) so employee data can be fetched from `VM_EmployeeMaster`. This means test comments/updates can write to `Test_OperationsDB`; use test records. For a no-network UI preview, set `SQL_API_MODE=mock` instead (the mock is in-memory and does not persist).

Before testing with Test API, set `DEV_USER_EMAIL` in your local `.env` to an actual `OffEmail` belonging to a row with `Active='Y'`. `local.user@hosexperts.com` is only a placeholder. Never commit `.env` or any SQL API token.

Useful endpoints:

- `GET /health` — health/mode summary
- `GET /api/whoami` — authenticated identity (employee code, name, email; no secrets)
- `GET /embed.js` — embeddable comments launcher for One Portal forms
- `GET /docs` — interactive FastAPI API documentation

Example task-context URL for local testing:

```text
http://127.0.0.1:8000/?tableName=Z_SalesOrder&fmsRefId=8&appId=APP000001&stageNo=1
```

`fmsRefId` in the URL is the actual record value (e.g. `8`). The mapping table's `FMSRefId` stores the source column name (e.g. `Pick ID`). These are different concepts. `CommentID` is generated by the app from `TableName + reference value + AppID + StageNo`; callers do not need to pass a Comment ID.

## Connect to the real One Portal login

1. Generate one shared secret once:

   ```powershell
   py -c "import secrets; print(secrets.token_urlsafe(48))"
   ```

2. Add the same generated `COMMENTS_LAUNCH_SECRET` to the private `.env`/environment of **both** the Comments backend and the One Portal backend. Do not commit the value, put it in HTML/JavaScript, or send it in a URL.
3. Copy `one_portal_integration/app/routers/comments_launch.py` into the existing One Portal repo at `app/routers/comments_launch.py`.
4. Follow `one_portal_integration/integration/MAIN_INCLUDE_SNIPPET.txt` to import and include that router in the One Portal FastAPI app. Keep the current JWT/session middleware protecting `/api/comments/launch-ticket`; it reads `request.state.user` populated by the existing middleware and ignores client-submitted identity fields.
5. Add `one_portal_integration/app/static/js/comments-launch-bridge.js` to the Portal static files only if the form is hosted in a cross-origin iframe. Configure exact trusted origins—never `*`.
6. Embed `/embed.js` into the form and provide the dynamic task values/selectors. See `docs/embed-widget.md` and `docs/portal-identity-handoff.md`.
7. In the Comments backend deployment set `APP_ENV=production` and `LOCAL_DEV_IDENTITY_ENABLED=false`. Serve it over HTTPS. For iframe use, configure cookies and hosts so browser third-party-cookie blocking does not break the session; a same-site subdomain/reverse proxy is preferred.

The ticket contains EmployeeCode and task context, not the browser-chosen email. The Comments backend validates the signature/expiry/one-time `jti`, resolves EmployeeCode against `VM_EmployeeMaster`, requires `Active='Y'`, and obtains `EmployeeName`/`OffEmail` from that row. The app saves Sender server-side using the verified `OffEmail`.

**Scaling note:** the current one-use ticket replay cache lives in process memory. Before running multiple Comments instances, move replay tracking to a shared Redis or SQL-backed nonce store.

## SQL schema

The verified comment log uses compact names: `RecordID`, `CommentID`, `FMSRefId`, `TaskID`, `StageName`, `AppID`, `AppName`, `Text`, `AttachmentURL`, `Timestamp`, `Sender`, `Receiver`, `AttachmentFilename`, `Type`, `AskID`, `Status`, `NotificationMessage`, `OpenThread`, `CompleteStatus`, `UniqueID`, `ThreadID`, `ThreadColor`, `Unique`, `ExtractedText`, `TimestampInText`.

The mapping table uses `FMSRefId`, `AppID`, `StageNo`, `TableName`. The `FMSRefId` column in that table is the *reference-column name* (e.g. `Pick ID`); the URL's `fmsRefId=8` is the *current row's value*.

- `sql/001_create_comment_tables.sql`: fresh-install tables, matching compact column names.
- `sql/002_add_table_name_to_fms_comment_fms_stage_map.sql`: upgrade the map to include `TableName` and the four-part key.
- `sql/003_rename_legacy_comment_log_columns_compact.sql`: optional migration from old spaced comment-log columns to compact names.

Review SQL scripts and run them on `Test_OperationsDB` first. They are not executed automatically by the application. Back up tables and check dependencies before migrating a database used by other apps.

## Employee names, mentions, and rights

The User tab and @mention suggestions read `VM_EmployeeMaster.EmployeeName`, `OffEmail`, `Active`, `RoleID`, and `Department`. Only `Active='Y'` employees are selectable. A sender's display name is resolved by matching the stored sender email to an active employee's `OffEmail`.

The agreed Admin rule is `RoleID IN (1,2,3)` **OR** Department token `Management`/`MDO` (case-insensitive). This rule controls the UI role display; any privileged backend operation must also enforce authorization server-side.
